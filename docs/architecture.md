# Архитектура

Актуально на 23.10.2026. Engine, editor, UI и frontend-стенд реализованы.
Backend пока представлен стартовым Adonis-приложением. Разделы о серверном хранении
и размещении описывают целевую архитектуру MVP, а не работающую инфраструктуру.
Продуктовые сроки, лимиты и правила — в
[продукте](product.md), последовательность работ — в [плане MVP](mvp-plan.md).

## Границы пакетов

| Путь                  | Ответственность                                                                     |
| --------------------- | ----------------------------------------------------------------------------------- |
| `apps/frontend`       | Vue SPA на Vite + Nuxt UI; текущий стенд, будущие кабинет и административный раздел |
| `packages/qr-toolkit` | Headless engine, сериализация содержимого/состояние редактора, локализация и Vue UI |
| `packages/theme`      | Переносимые токены QR Studio и адаптер Nuxt UI                                      |
| `apps/landing`        | План: Astro с общим Vue editor                                                      |
| `apps/backend`        | Стартовое AdonisJS API; цель MVP — PostgreSQL, сессии, динамика, аналитика и фоновые процессы |
| `packages/shared`     | Резерв для общих API-контрактов                                                     |

Монорепозиторий использует pnpm Workspaces. Корень не содержит зависимостей;
инструменты принадлежат пакетам, локальные связи — `workspace:*`.
Redis, очереди, микросервисы и дополнительный оркестратор сборки добавляются по необходимости.

## Поток данных и владение

```text
Форма → Valibot / payload builder → строка → encodeQr → QrMatrix
  → renderQrSvg → SVG preview / файл → браузерная растеризация PNG
```

- `/engine`: адаптер `qr` от Paul Miller и собственный синхронный SVG Renderer, без Vue/DOM.
  Матрица содержит маску служебных зон; renderer не знает о типах содержимого или пресетах.
- `/editor`: состояние, независимые черновики, схемы/сериализация и контракт конфигурации, без Vue/DOM.
- `/ui`: Vue-компоненты и composables, загрузка логотипа, preview и браузерный экспорт.
  Изменения оформления переиспользуют матрицу; устаревшие асинхронные результаты не заменяют актуальные.
- Приложение выбирает конфигурацию, каталог пресетов, локаль и внешние сервисы.
  Состояние (`v-model`) отделено от доступных инструментов (`config`).
- Ошибки/диагностика содержат `code + params`; UI выбирает словарь RU/EN или свой.

Публичные контракты и примеры — в [README toolkit](../packages/qr-toolkit/README.md).
Engine/editor/i18n собираются в ESM и декларации; `/ui` поставляется исходниками.
Vue и Nuxt UI — optional peers, обязательные для UI-потребителя.

## Интеграция frontend

Frontend владеет Nuxt UI Vite/runtime plugin, одним `UApp` и импортом глобального CSS в `main.ts`.
Общая [тема QR Studio](../packages/theme/README.md) использует локальные Manrope и Remix Icons.
Vite компилирует UI toolkit из исходников; `resolve.dedupe` объединяет Vue/Nuxt UI,
`scanPackages` и Tailwind `@source` охватывают toolkit.
Vite-конфигурация импортирует тему по относительному пути: так её TypeScript входит
в bundle конфигурации и отслеживается при изменениях, а не кэшируется как внешний пакет.
Обнаружение используемых Nuxt UI-компонентов включено только при сборке: в dev список
не обновляется при HMR, из-за чего новый компонент может остаться без стилей.

`prepare:ui` генерирует локальный контекст `#build/ui` в `node_modules/.nuxt-ui` без запуска сервера.
Он вызывается при проверке типов и запуске frontend; auto-import и его декларации отключены.
Генерируемые файлы не редактируются вручную. Версии инструментов закреплены в пакетах/lockfile;
TypeScript 6 выбран из-за несовместимости используемого vue-tsc с TypeScript 7.
Правила линтера и форматирования определяются `.oxlintrc.json` / `.oxfmtrc.json` пакетов.

## Карта и внешние запросы

OpenLayers с растровыми тайлами OpenStreetMap загружается лениво при открытии карты координат.
API-ключ не нужен; атрибуция обязательна, предзагрузка отключена. При недоступной карте
ручной ввод координат продолжает работать. Условия [сервера тайлов](https://operations.osmfoundation.org/policies/tiles/).

Поиск по названию использует [Photon](https://github.com/komoot/photon#demo-server), только по явной отправке.
Запросы ограничены по частоте, результаты кэшируются и проверяются Valibot;
отменённые/устаревшие ответы игнорируются. Другой провайдер задаётся через `locationSearch`.
Публичные серверы не имеют SLA; генерация QR не отправляет им payload или логотип,
но карта загружает тайлы, а поиск отправляет введённое название места.

[Патч OpenLayers](../patches/ol@10.11.0.patch) разрешает пассивный wheel-listener через
`wheelListenerPassive: true` при `mouseWheelZoom: false`, чтобы колесо прокручивало страницу.
При обновлении библиотеки нужно перепроверить патч. UI-тесты используют реальную карту,
подменяя сетевые тайлы и ответы поиска локальными fixtures.

## Целевая архитектура backend

В `apps/backend` создан стартовый API на AdonisJS 7 с PostgreSQL. Базовые маршруты
регистрации, входа, профиля и выхода используют guard `web`; access tokens удалены.
Данные сессий хранятся в PostgreSQL, cookie содержит только идентификатор сессии.
При входе идентификатор меняется, при выходе старый идентификатор теряет доступ.
Cookie ограничена текущим хостом, использует HttpOnly и SameSite=Lax, а в production
также Secure; это требует HTTPS. Remember-me пока отключён.

Для SPA предусмотрен `GET /api/v1/auth/csrf`: он выдаёт cookie сессии и читаемую
JavaScript cookie `XSRF-TOKEN`. Клиент отправляет запросы с `credentials: "include"`,
а для POST/PUT/PATCH/DELETE — значение XSRF-cookie в заголовке `X-XSRF-TOKEN`.
Неверный или отсутствующий CSRF-токен возвращает JSON с HTTP 403, включая вход
и регистрацию. CORS допускает credentials только для явно заданных origins
в `CORS_ORIGIN`; без списка разрешены браузерные запросы с того же origin.
В dev frontend и API должны использовать одинаковое имя хоста (localhost либо
127.0.0.1), чтобы host-only cookie была доступна клиенту.

Это основа, а не завершённые сценарии аккаунтов MVP: подтверждение email,
восстановление доступа и ограничения запросов ещё предстоит реализовать.
SQL-схема остальных областей, API, индексы и агрегирование уточняются по этапам.

Линтинг и форматирование backend выполняют Oxlint и Oxfmt с теми же базовыми
правилами и стилем, что в остальных пакетах; окружение линтера — Node.js.
Генерируемые `.adonisjs/`, `database/schema.ts`, сборка и временные файлы исключены
из обеих проверок. Импорты `reflect-metadata` и `@poppinss/ts-exec` разрешены
для инициализации runtime. Команды — в [README](../README.md#проверки).
Backend входит в общий pnpm workspace: lockfile и разрешения сборки нативных
зависимостей хранятся в корне монорепозитория.

Общие API-контракты при необходимости размещаются в packages/shared.
Engine/editor не получают зависимости от аккаунтов, БД, подписок или серверного хранения.

### Домены и доступ

| Хост | Ответственность |
| --- | --- |
| Основной домен | Astro-лендинг и публичный статический редактор |
| app.<домен> | Кабинет, административный раздел и API |
| r.<домен> | Короткие ссылки динамических QR |

Конкретный домен выбирается до публичного запуска. Существующие адреса сохраняются;
изменение основного бренда или маршрутизации не должно ломать напечатанные QR.
Cookie сессии ограничена хостом кабинета и не отправляется на хост редиректов.
Cookie аналитики относится к хосту редиректов и отделена от аутентификации.
Браузерные защиты сессий, CSRF и доверие proxy настраиваются при реализации.
Изоляция ресурсов по владельцу и административные права проверяются backend.

### Логическая модель данных

| Группа | Ответственность |
| --- | --- |
| Аккаунты, сессии, подтверждение и восстановление доступа | Идентификация, права, часовой пояс, удаление аккаунта |
| Пробный доступ | Даты и история административного продления; не перезапускается удалением QR |
| Динамические QR и история назначений | Постоянный адрес, собственный дизайн, назначение и жизненный цикл |
| Кампании | Текущая группировка QR; историческая принадлежность фиксируется в событиях |
| Пресеты и ассеты | Именованные дизайны, ссылки на файлы и их использование |
| События и производные агрегаты | Исходная история переходов и ускорение отчётов |
| Проверки ссылок, жалобы, блокировки и аудит | Решения безопасности, причины и авторы действий |
| Фоновые задания и уведомления | Планирование, повторные попытки, результат выполнения |

Это области ответственности, а не окончательный список SQL-таблиц.
Ручную паузу, блокировку сервиса и ограничения доступа нужно различать:
снятие одного ограничения не должно снимать остальные.
Механизм лимитов и удаления согласуется с конкурентными запросами, продлением
и восстановлением. Минимальная запись занятого короткого адреса сохраняется
после очистки данных QR, чтобы исключить повторную выдачу.

В будущих коммерческих этапах право разовой покупки закрепляется за конкретным QR
и отделяется от подписки аккаунта. На MVP платежный провайдер, биллинг и покупка
не реализуются; продуктовые условия — в [продукте](product.md).

### Дизайны и файлы

Пресет и собственный дизайн QR хранятся как версионируемые настройки, например JSON.
Дизайн не содержит назначение и статистику; при применении пресета настройки копируются.
Файл логотипа хранится отдельно, в JSON остаётся ссылка на ассет и параметры размещения.
Ассеты принадлежат владельцу; общий файл в рамках аккаунта можно переиспользовать.
Схема ссылок должна позволять безопасно определять, когда файл больше не используется.

Сейчас toolkit принимает встроенный raster data URI. Приложение отвечает за получение
сохранённого файла и преобразование серверного представления в состояние редактора;
engine не должен сам загружать удалённые URL. Серверное сохранение — явное действие host.
Проверки формата, размера и допустимого изображения выполняются также на сервере;
числовые ограничения и допустимые форматы берутся из кода редактора.

Пользовательский сохранённый пресет полного дизайна не следует смешивать с текущим
API каталога QrDesignPreset: действующее применение каталога сохраняет ряд настроек,
включая логотип, см. [toolkit](../packages/qr-toolkit/README.md#vue-editor).
Интеграция полных сохранений планируется в приложении; существующий API нельзя
считать изменённым одной правкой документации.

Логотипы находятся в постоянном Docker volume. Очистка учитывает ссылки пресетов,
действующих QR и QR в корзине. Скачанные SVG/PNG по-прежнему формируются в браузере;
постоянное серверное хранение экспортированных изображений не требуется.

### Редиректы и проверка назначений

Короткий адрес имеет вид https://r.<домен>/<code>. Backend разрешает его в проверенное
назначение и отвечает временным редиректом 302/307. Постоянный 301 не подходит
для сменяемой цели. Произвольный открытый redirect endpoint не нужен.

Проверка URL выполняется на границе API: допустимые схемы и структура, отсутствие
встроенных учётных данных и прямых циклов через собственные ссылки.
При необходимости сетевых запросов требуется отдельная защита от SSRF;
скачивание целевых страниц самим backend не является обязательной функцией MVP.

Внешние проверки угроз выполняются при создании/смене назначения и периодически.
Проверяемый кандидат не заменяет действующее назначение до результата проверки.
Новый QR ожидает активации. Ошибка провайдера и обнаружение угрозы — разные результаты:
первая требует повторной попытки, второе — блокировки и уведомления.
Провайдер не вызывается синхронно при каждом сканировании.

Правила угроз, жалоб, ложных срабатываний и противоправного контента уточняются
на этапе реализации до публичного запуска. Эти ограничения независимы от будущей оплаты.

### Аналитика

Событие связывает QR, владельца, время, кампанию и действовавшее назначение на момент
перехода, идентификатор браузера и разобранные аналитические признаки.
Время хранится в UTC; фильтрация и группировка используют часовой пояс аккаунта.
Исходные IP и полный User-Agent в долгосрочную аналитическую историю не входят.
География обогащается выбранным провайдером; его ещё предстоит определить.

События сохраняются для отчётов и произвольной детализации внутри доступного окна;
агрегаты являются производными. Одних дневных счётчиков недостаточно для точных
уникальных посетителей за произвольный период с фильтрами.
Нужно определить стратегию запросов, индексов и агрегирования с учётом этого ограничения.
Правила подсчёта, срок cookie и доступное окно задаёт [продукт](product.md).

Сбой записи/обработки аналитики не останавливает редирект. Механизм записи,
контроль потерь/дублей и допустимые ограничения полноты уточняются при реализации.
Окончательное удаление QR очищает связанные события и корректирует производные
агрегаты, чтобы не оставлять скрытую бессрочную историю.
Технические журналы для антиабьюза отделены от пользовательской аналитики;
их состав и сроки хранения требуют отдельного решения.

### Фоновые процессы и email

На MVP планируется отдельный worker с заданиями в PostgreSQL, без обязательного Redis.
Отправка писем, повторные проверки ссылок, напоминания и очистка не должны зависеть
от того, открыт ли у пользователя кабинет. Конкретный механизм заданий выбирается
при реализации.

Операции должны выдерживать повторы и перезапуски; изменения БД и постановка
критичных задач согласуются транзакционно. Задания повторно проверяют актуальные
сроки, блокировки и состояние аккаунта: продление может отменить прежнее удаление
или сделать напоминание неактуальным. Время фактической очистки не должно
продлевать доступ за установленную дату.

Email отправляется внешним сервисом через SMTP/API с подтверждённого домена;
настраиваются SPF, DKIM и DMARC. Приём ответов поддержки настраивается отдельно.
Нужны повторные попытки, результат доставки и защита от повторной отправки
одного уведомления при повторной обработке задания.
Сбой отправки не блокирует редиректы. Провайдер и расписание писем выбираются
на этапе реализации.

## Размещение и эксплуатация MVP

Один сервер, Docker Compose и Caddy. Caddy отвечает за HTTPS и маршрутизацию
основного домена и поддоменов; приложения, worker и PostgreSQL работают в контейнерах.
База доступна только во внутренней сети. Секреты не коммитятся и не входят в образы.

БД, логотипы и необходимые данные Caddy сохраняются в постоянных volumes.
Резервные копии БД и файлов хранятся вне этого сервера; проверяется согласованное
восстановление ссылок и файлов. Volume сам по себе не является резервной копией.
Провайдер, расписание, сроки хранения копий и обработка удалённых данных
уточняются до публичного запуска.

Мониторинг должен охватывать доступность редиректов, ошибки API, состояние worker,
отставание задач, отправку писем, резервные копии, место на диске и объём аналитики.
Один сервер остаётся общей точкой отказа; распределённое размещение в MVP не требуется.
